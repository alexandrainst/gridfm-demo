Demonstration of how federated learning can train a foundation model for the power grid.

The demo trains a [gridfm-graphkit](https://github.com/gridfm/gridfm-graphkit) power
flow model with the federated learning framework [Flower](https://flower.ai/) across
several clients. Each client contains its own synthetic dataset, generated by
[gridfm-datakit](https://github.com/gridfm/gridfm-datakit) from fictional grid
topologies.

## Background

### Federations

A federation is a set of clients and their synthetic data. Each one is a folder in
`federations/` with a Docker Compose file and a gridfm-datakit config per client.

- `case14_2clients`: two clients on the IEEE 14-bus grid (`case14_ieee` from PGLib).
  Each client generates 20 load scenarios from an aggregated load profile, each in two
  topology variants with one random line or generator removed, and perturbs generator
  costs and line admittances. The clients share these settings and differ only in their
  random seed (1001 and 2001), so their data comes from the same distribution. Both
  clients train on the host's NVIDIA GPU.
- `case500_2clients`: two clients on different PGLib grids, client 0 on the 500-bus
  `case500_goc` and client 1 on the 588-bus `case588_sdet`. Each client generates 500
  load scenarios from an aggregated load profile, each in four topology variants with
  one random line or generator removed, and perturbs generator costs and line
  admittances. The clients differ in their grid and their random seed (1001 and 2001).
  Both clients train on the host's NVIDIA GPU.
- `case300_1client`: one client on the 300-bus `case300_ieee` from PGLib, with the data
  settings of `case500_2clients` and random seed 3001. It is unseen test data for the
  models trained on `case500_2clients`, which `notebooks/case300_comparison.py` compares
  on it. The experiments wait for two clients, so none of them trains on this
  federation.

### Experiments

An experiment is a training procedure run on a federation. Each one is a package in
`flower_app/experiments/`, and its run config defaults are in the
`[tool.flwr.app.config.<experiment>]` table of `pyproject.toml`.

- `fedavg`: trains the gridfm-graphkit `GNS_heterogeneous` power flow model with
  Flower's FedAvg strategy. In each round, every client trains the global model for
  `local-epochs` epochs on its own data with the `MaskedBusMSE` loss, and the server
  averages the client models weighted by their number of training examples. Every client
  then reports its validation loss on the new global model. The defaults are
  `num-server-rounds = 3`, `local-epochs = 3` and `seed = 0`.
- `fedavg_large`: `fedavg` with the model at gridfm-graphkit's default size, a hidden
  size of 48, 12 layers and 8 attention heads, for grids of several hundred buses. It
  trains until the clients' averaged validation loss has not improved for `patience`
  rounds, for at most `max-server-rounds` rounds, and saves the global model of the
  round with the lowest validation loss. The defaults are `max-server-rounds = 300`,
  `patience = 3`, `local-epochs = 1` and `seed = 0`.
- `isolated_large`: each client trains the model of `fedavg_large` on its own data only,
  with the `MaskedBusMSE` loss, until its validation loss has not improved for
  `patience` epochs, for at most `max-epochs` epochs. It reports its lowest validation
  loss. The models are not aggregated. The server saves each client's model of the epoch
  with the lowest validation loss as `final_model_client_<id>.pt`. The learning rate
  decays after 2 epochs without improvement. The defaults are `max-epochs = 300`,
  `patience = 3` and `seed = 0`.

## Requirements

- [uv](https://docs.astral.sh/uv/getting-started/installation/)
- [Docker](https://docs.docker.com/get-docker/) with Docker Compose
- A C++ compiler, such as `g++`, for building `torch-scatter`
- An NVIDIA GPU and the
  [NVIDIA Container Toolkit](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html)
  for training

## Usage

Run the demo with the `gridfm` command. Each command takes a federation from
`federations/` or an experiment from `flower_app/experiments/` as its argument, and asks
for one if it is left out. [Background](#background) describes the available federations
and experiments, and `uv run gridfm --help` lists all commands.

### Generate Data

Generate the synthetic data of each client in a federation. The data is written to
`federations/<federation>/data/`, and clients that already have data are skipped:

```bash
uv run gridfm data <federation>
```

### Start the Federation

Start the federation in the background. This builds the Docker images, starts the
SuperLink, one SuperNode and ClientApp per client, and the ServerApp:

```bash
uv run gridfm up <federation>
```

### Run an Experiment

Run an experiment on the running federation and stream its logs. The run writes its
results to `outputs/<federation>/<experiment>/<timestamp>/`, where `<timestamp>` is the
UTC start time of the run:

```bash
uv run gridfm run <experiment>
```

### Predict Scenarios

Predict every scenario of every client with the model of a finished run. The run is
given as `<experiment>/<timestamp>`, and only experiments that save a model, such as
`fedavg`, can be predicted. The predictions are written to
`predictions/<federation>/<experiment>/<timestamp>/`, replacing earlier ones:

```bash
uv run gridfm predict <federation> <run>
```

### Plot Predictions

Run the notebook that plots the predictions of a run on the network of one scenario as
an app. It reads `predictions/` and the client data, and writes nothing:

```bash
uv run marimo run notebooks/scenarios.py
```

Replace `run` with `edit` to open the notebook in the editor instead.

### Compare Models on an Unseen Grid

Run the notebook that compares the `fedavg_large` model and the two `isolated_large`
models of `case500_2clients` on the data of `case300_1client`. It predicts with the
models itself and writes nothing:

```bash
uv run marimo run notebooks/case300_comparison.py
```

### Stop the Federation

Stop the federation and remove its containers. The generated data and the outputs are
kept:

```bash
uv run gridfm down <federation>
```

### Delete Data

Delete the generated data of the federation after asking for confirmation:

```bash
uv run gridfm clean <federation>
```
